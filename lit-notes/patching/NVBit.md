## Intro 

Binary instrumentation is a powerful technique that allows for the transformation of binaries for a bunch of purposes: 
- application profiling 
- performance modeling
- error checking 
- fault injection
Binary instrumentation (BI) is also one of the backbones of modern comp arch research. Notable examples of such tools are ATOM, PIN and DynamoRIO for CPUs. All these frameworks implement some soft of dynamic binary rewriting without needing application source code. 

With GPUs growing in usage, a need for a GPU equivalent is obvious. Compiler based tools such as SASSI and Ocelot have helped but have significant practical limitations:
- They need the source code recompilation which is an issue for large code base or if the code is proprietary 
- They are tied to a specific compiler (pr compiler version)
- They cannot target code generated by the GPU driver via JIT-compilation of PTX code. 
- They require compile time selection of the instrumentation sites, functions and params types: and therefore they cannot adapt the instrumentation based on dynamic behavior. 

This paper presents NVBit, a dynamic BI framework for targeting NVIDIA GPUs. NVbit provides a rich high level API that allows instruction inspection, callbacks to CUDA driver APIs and injection of arbitrary CUDA functions into any applications before the kernel launch. Operating the SASS level using dynamic recompilation, NVBit analyzes GPU kernel registers to generate ABI compliant instrumentation. 

This works makes the following contributions:
- Develop NVBit user-level API which can be used to inspect/instrument instructions and intercept cuda driver API calls
- Describe NVBit's underlying working principles, mechanisms and implementation details. 
- Provide examples of instrumentation tools and reason about the [[Instruction Set Architecture]] extensions. 

## Background 

### GPU Architecture 

GPUs have threads and [[CUDA Programming Model#Thread Hierarchy|warps]] with a thread have up to 255 general purpose registers that allow access to global, shard and constant mem. Divergence of control flows is handled via per-warp active masks that enable/disable thread with specific control flows. 

If you need more background on the memory you can also check the [[CUDA Runtime|GPU memory model and hierarchy]]. 

### GPU Software Stack 

NVBit targets the cuda compute stack. A user can write parallel programs using cuda an NVCC to generate intermediate code in a virtual ISA called PTX. PTX exposes the GPU as a data-parallel computing device by providing a stable programming model & the instruction set for general purpose parallel programming, but PTX does not directly run on the GPU. A back-end compiler optimizes the PTX instructions into SASS machine code that runs on a specific device, this backend compiler can be invoked in two ways:
1. Ahead-of-time via *ptxas* PTX assembler
2. At run-time using JIT compiler in the GPU driver. 

NVBit interacts directly with the cuda driver and handles machine code after it has been compiled into SASS. 

## High Level View 

From a high level view, NVBit is a single static library (`libnvbit.a`) and the header file (`nvbit.h`). An NVBit tool is created by either developing a `.cu` file using the NVBit API or compiling it with NVCC, or linking with the static library. This process generates a shared library which is usually (in Linux) with the `.so` file extension. Many shared libraries can be created but only a single library can be injected on a target at run-time. 

To use NVBit tool (i.e. share lib) developers inject functionality at run-time into application that use the cuda driver. The injection is based on `LD_PRELOAD`, an optional environment var under Linux that contains one ore more paths to a share lib, indicating that the load should load this share object before other libs.

From a user's perspective, the typical tool will implement one or more GPU device functions which are injected in an application's kernel according to the defined injection points. This is typically done when the kernel is launched for the first time but it can be done at other times within the cuda driver callbacks. 

```cpp
/* NVBit include, any tool must have it */
#include "nvbit.h"

/* Counter variable used to count instructions */
__managed__ long counter = 0;

/* Used to keep track of kernels already instrumented */
std::set<CUfunction> instrumented_kernels;

/* Implementation of instrumentation function */
extern "C" __device__ __noinline__ void incr_counter() {
    atomicAdd(&counter, 1);
} NVBIT_EXPORT_DEV_FUNC(incr_counter);

/* Callback triggered on CUDA driver call */
void nvbit_at_cuda_driver_call(CUcontext ctx,
    int is_exit, 
    cbid_t cbid, 
    const char *name,
    void *params, CUresult *pStatus) {

    /* Return if not at the entry of a kernel launch */
    if (cbid != API_CUDA_cuLaunchKernel || is_exit)
        return;

    /* Get parameters of the kernel launch */
    cuLaunchKernel_params *p = (cuLaunchKernel_params *) params;

    /* Return if kernel is already instrumented */
    if(!instrumented_kernels.insert(p->func).second)
        return;

    /* Instrument all instructions in the kernel */
    for (auto &i: nvbit_get_instrs(ctx, p->func)) {
        nvbit_insert_call(i, "incr_counter", IPOINT_BEFORE);
    }
}

/* Callback triggered on application termination */
void nvbit_at_term() {
    cout << "Total thread instructions " << counter << "\n";
}
```

This code snippet counts every thread level instruction executed, then prints the counter at the end of the application. The macro is used to prevent the compiler from removing dead code as it is not called anyone explicitly. The callback

## User Level APIs 

#### Callback API

The callback APIs are triggered by the NVBit core when a specific event in the target is encountered. These events are application start, termination, entry/exit of any cuda driver API call. The user can inspect and instrument the `CUfunctions` of the current running application using the cuda driver callbacks. For example, when a kernel is launched a callback `nvbit_at_cuda_driver_call` occurs with one of the params being the `CUfunction` launched. NVBit's callback interface uses similar event enums as CUPTI 

#### API inspection 

```cpp
/* Gets plain instructions of a CUfunction */
const std::vector<Instr*>&
	nvbit_get_instrs(CUcontext c, CUfunction f);
/* Gets basic blocks of a CUfunction */
const std::vector<std::vector<Instr*>>&
	nvbit_get_basic_blocks(CUcontext c, CUfunction f);
/* Gets related CUfunctions of a CUfunction */
std::vector<CUfunction>
nvbit_get_related_funcs(CUcontext c, CUfunction f);
```

this is the main way to retrieve and inspect the instruction composing a `CUfunction`. The inspection API provides two different views of the kernel bodies.
1. One view presents the body as a flat vector of the kernel instructions in program order. In the absence of ICF instructions the API returns the body as a vector of vectors of instructions where each sub-vector is a basic block. Such a block is an uninterrupted sequence of instructions including predicated instructions that each thread will execute without changing the control flow. 


#### Instrumentation API 

Such a tool can use the API to inject multiple device functions before or after any or all of the kernel's instructions. To inject a function, one needs to use the `nvbit_insert_call` and specify the location & the name of the function to inject. 

Such functions are injected by name because of their code location (i.e PC) is unknown at run-time. One can add arguments to the inject function such as register, predicate and immediate values using `nvbit_add_call_arg`.  These must match the func signature of the func to be injected. 

It is also possible to remove or replace original instruction using `nvbit_remove_orig` for example when replacing the original instruction with an eq. function. When NVBit replaces an instruction, it cannot guarantee that the original kernel will work as expected.

#### Control API

One can control instrumentations at run-time, for example, to dynamically select the execution of an instrumented or non-instrumented version of a func. At run-time the framework will select one version or the other, based on the last value set by the user with the call `nvbit_enable_instrumented`. The user can reset applied instrumentations at any time. This op may be performed at any point inside the callback `nvbit_at_cuda_driver_call`, even while the application is executing.

This allows for instr funcs to be rewritten on the go depending on the dynamic condition's of the kernel's execution. A bit advancement over static-based GPU instrumentations. 

#### Device API 

NVBit provides a device level API that can be used within the injected funcs. Most importantly it is possible to read & write any register used by the kernels or device funcs using this API. 

While arbitrary writes of register values may cause catastrophic application level errors, the ability to modify GPU state is a req. for uses cases such as fault injections or instruction emulation.

## Use Case Examples

### Memory Access Address Divergence 

Understanding mem patterns is very important when optimizing an app or designing memory subsystems. NVBit allows one to easily extract this info by instrumenting every mem op to collect reference addresses, which can then be directly analyzed on device or sent to the host for further processing.
